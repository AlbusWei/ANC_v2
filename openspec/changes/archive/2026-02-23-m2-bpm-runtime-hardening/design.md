## Context

`m2-bpm-runtime-hardening` targets governance hardening with runtime gate closure. The requirement is to keep each round auditable via Entire checkpoint linkage, OpenSpec state evidence, and construction-plane status visibility, then close the change only after live regression and gate reconciliation pass.

Key constraints:
- Fail-Closed on missing evidence, protocol mismatches, or missing `Entire-Checkpoint` trailers.
- Thread-based delivery must remain commit-auditable and round-isolated.
- M6 Thread 6 must run one live regression (non-simulated), and may not declare done when prior checkpoint/commit linkage is broken.

## Goals / Non-Goals

**Goals:**
- Define a minimal baseline that is immediately apply-ready and auditable.
- Standardize evidence surfaces (`checkpoint_commit_map.jsonl`, `git_range.txt`, live-regression plan, test harness files).
- Ensure construction-plane progresses from `In Progress` to close-out only after `verify/verify-m2/verify-m6` + live regression all pass.

**Non-Goals:**
- Rewriting BPM runtime core modules in this thread.
- Introducing new production dependencies for runtime logic.

## Decisions

### Decision 1: Evidence-first sequencing
- Choice: establish test/evidence/plan scaffolding before runtime code changes.
- Rationale: this ensures Thread 1~6 commits are attributable and verifiable from the first code-change round.
- Alternative considered: backfill evidence at the end of M2. Rejected because missing early-round metadata cannot be reconstructed reliably.

### Decision 2: JSONL for checkpoint/commit mapping
- Choice: use append-only `checkpoint_commit_map.jsonl` with fixed minimum fields.
- Rationale: JSONL supports per-round incremental writes, simple diffs, and deterministic audit replay.
- Alternative considered: maintain a single mutable JSON object. Rejected due to merge conflict risk and weaker chronology.

### Decision 3: Separate live-regression plan from execution evidence
- Choice: pre-embed `m6_live_regression_plan.md` and keep runtime execution outputs in evidence files generated by later threads.
- Rationale: decouples policy (what must be validated) from run artifacts (what was observed) and clarifies pass/fail gates for Thread 6.
- Alternative considered: inline plan inside Thread 6 notes only. Rejected because upstream threads would not share a stable contract.

### Decision 4: Construction-plane gate integrity
- Choice: mark change `In Progress` during build rounds and close `Q-001` only after Thread 6 gate closure checks pass.
- Rationale: reflects real execution progress while preserving fail-closed close-out discipline.
- Alternative considered: keep `Q-001` permanently open in this change. Rejected because gate evidence now covers closure criteria.

## Risks / Trade-offs

- [Risk] Evidence schema drift across threads. → Mitigation: lock minimum fields in plan/spec and validate each round before commit.
- [Risk] Commit misses `Entire-Checkpoint` trailer. → Mitigation: mandatory post-commit `git log -1 --pretty=raw` verification; Thread 6 fail-closed rule.
- [Risk] Live regression blocked by environment instability. → Mitigation: capture environment prerequisites in the plan and mark blockers explicitly with timestamped evidence.

## Migration Plan

1. Complete Thread 0 scaffold and set OpenSpec to apply-ready.
2. In Thread 1~5, append checkpoint/commit mapping after each commit.
3. In Thread 6, collect git range, run live regression once, reconcile mapping, and close only when all gates pass.
4. If any gate fails, keep status In Progress and record failure evidence for the next round.

Rollback strategy:
- If scaffold files are malformed, revert only scaffold artifacts and rerun Thread 0 with corrected evidence schema.
- If mapping records are inconsistent, append corrective record rather than rewriting historical entries.
