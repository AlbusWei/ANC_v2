# Registry 治理架构决策记录

最后更新：2026-02-21  
状态：Active

> 本文档记录 registry 治理的架构级决策与设计动机。
> 目标是提供可复用的治理框架，而非一次性配置说明。

## 决策范围

覆盖对象：

1. 资产注册层（agent/skill/process）
2. 契约验证层（schema + fail-closed）
3. 运行投影层（registry -> runtime config）
4. 门禁执行层（pre-commit/CI）

## ADR-01：机器真相源优先于人工文档

决策：

1. registry 的 `entry_contract` 作为机器真相源。
2. 人类可读 schema 文档由机器生成，不作为权威输入。

动机：

1. 避免“文档说一套、数据是一套”的双真相漂移。
2. 让校验与协作说明共享同一事实源。

## ADR-02：Fail-Closed 的结构化实现

决策：

1. 契约采用封闭字段模型（unknown 字段拒绝）。
2. 字段类型、枚举、模式、嵌套要求都进入可执行契约。

动机：

1. 结构错误在写入时立即阻断。
2. 把治理规则从“约定”升级到“可执行约束”。

## ADR-03：资产模型与运行模型解耦

决策：

1. registry 表达资产事实与治理元数据。
2. runtime config 作为投影结果，不反向定义资产事实。

动机：

1. registry 与运行时对象并非同构。
2. 解耦后可在不改资产模型的前提下演进运行配置。

## ADR-04：受管区投影（Managed Surface）

决策：

1. 投影工具只维护明确受管区。
2. 非受管区由治理流程（BPM 审批 + admin 执行）维护。

动机：

1. 自动化与人工治理各守边界，避免互相覆盖。
2. 支持渐进治理，不强制一次性全量自动化。

## ADR-05：稳定标识作为执行引用键

决策：

1. 运行引用使用稳定 ID，而不是展示名称。
2. 展示名允许演进，不影响执行链路与审计关联。

动机：

1. 防止改名导致隐式断链。
2. 保证流程实例、投影键、审计证据的一致可追溯性。

## ADR-06：混合投影策略（bundle + pin）

决策：

1. 支持目录聚合投影与单资产精确投影并存。
2. 当两者冲突时，pin 作为更具体声明优先。

动机：

1. 兼顾规模化维护成本与关键资产可控性。
2. 保持策略单一（同一冲突规则）以避免歧义。

## ADR-07：生命周期门禁与开发例外

决策：

1. 生命周期状态直接参与投影门禁。
2. 开发期例外必须显式声明，不允许隐式放行。

动机：

1. 把“可运行”与“可治理”绑定到同一状态机。
2. 兼顾研发流畅性与治理可解释性。

## ADR-08：Profile 化投影而非环境分叉

决策：

1. 采用 profile 定义投影变体（如基础版/入口版）。
2. 同一投影引擎生成不同目标，避免手工分叉维护。

动机：

1. 用参数化而非复制粘贴实现环境差异。
2. 降低多配置片段长期漂移风险。

## ADR-09：治理流程优先于工具便利

决策：

1. 系统级写操作仍由治理流程控制，不因工具自动化而绕过。
2. 工具负责可重复执行与一致性验证，不替代审批责任链。

动机：

1. 避免“自动化即授权”的错误等价。
2. 保持角色职责与升级链清晰。

## ADR-10：演进友好（对流程层级重构的兼容）

决策：

1. 将本轮重点放在 registry 契约与投影框架。
2. 流程层级与递归字段的强约束延后到层级重构稳定后再收敛。

动机：

1. 在上游设计仍迭代时避免过早硬化。
2. 先稳住治理骨架，再收紧流程语义细节。

## 使用方式

1. 架构讨论先引用本决策，再落字段与命令。
2. 新增规则时先补一条 ADR，再改契约。
3. 若发生冲突，遵循：Objective > Spec > Test > Implementation。
