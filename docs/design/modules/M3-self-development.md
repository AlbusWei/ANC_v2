# M3 — 反身自开发模块详细设计

> 版本: v0.3.0 | 建设优先级: P1

## 模块定位

让系统具备“开发自己”的可执行流程能力。

## 模块边界

1. `M3` 负责开发执行闭环，不直接负责生命周期状态裁决。
2. `M3` 可以在 `draft` 级开发先行，但进入 `review/active` 必须通过 `M4`。
3. `M3` 复用 `M1` 的测试与门禁，不重复建设测试评估引擎。

## 核心资产

1. development-process（canonical）
2. full-development（规划）
3. skill-creator / agent-creator / process-creator

## 依赖关系（类型化）

1. 依赖 `M2`（`R/E`）：流程编排、实例状态与证据归档。
2. 依赖 `M1`（`T`）：Objective/Spec/Test 门禁与回归判定。
3. 依赖 `M4`（`G`）：生命周期审批、registry 同步与状态迁移。
4. 依赖 `M6`（`E`）：阶段目标、风险与执行纪律对齐。

## 与 M4 的并行策略

1. 并行原则：`M3` 与 `M4` 可并行建设。
2. 汇合门：`M3` 产出的新资产要进入 `review/active` 时，必须经过 `M4` 审批链。
3. 禁止项：未过 `M4` 门禁的资产不得被标记为可发布。

## 双主线关系

1. 内部主线直接依赖 M3。
2. 外部交付主线在 delivery-iterations 阶段复用 M3 能力。

## Fail-Closed 规则

1. Objective/Spec/Test 任一断链，拒绝进入实现与发布阶段。
2. 测试门禁失败，禁止推进生命周期状态。
3. lifecycle 证据缺失，拒绝状态迁移并升级 `owner -> bpm -> admin`。

## 风险与缓解

1. 风险：并行建设导致 `M3/M4` 边界漂移。
缓解：以“`M3 draft` 先行，`review/active` 必须经 `M4`”作为硬门禁。
2. 风险：外部交付复用时绕过内部质量门。
缓解：强制复用 `M1` 门禁与 `M4` 生命周期审批。

## 验收

- [ ] 至少一条内部产品链路完整跑通
- [ ] 新资产能进入 review 并通过门禁
- [ ] `M3` 与 `M4` 并行建设下边界不冲突
- [ ] 外部 `delivery-iterations` 复用不绕过内部门禁
